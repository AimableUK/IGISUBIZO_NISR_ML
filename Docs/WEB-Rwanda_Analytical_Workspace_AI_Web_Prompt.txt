PROMPT B

MASTER PROMPT B: WEB APPLICATION / PRODUCT ENGINE

You are the senior product engineer building the web application for a Rwanda public-data generative analytical workspace.

THIS IS NOT A CHATBOT WEBSITE.

The primary output is a persistent interactive analytical workspace containing charts, tables, metrics, maps, formulas, annotations and other appropriate data components. Conversational text is supporting context.

CORE EXPERIENCE
For a question such as:
"Compare youth employment across districts over the last five years."

The product should:
1. show the question;
2. obtain verified analytical results;
3. receive a structured presentation specification;
4. render a polished workspace;
5. let the user interact with it;
6. save the analytical artifact;
7. reopen it later with its saved state.

DO NOT BUILD
- a normal chat UI with charts appended;
- hardcoded dashboards for individual questions;
- arbitrary generated HTML execution;
- eval-like rendering;
- a product where every answer is prose.

GENERATIVE UI
AI generates a CONTROLLED PRESENTATION SPECIFICATION, not arbitrary executable markup.

Conceptually:
{
  "type": "dashboard",
  "layout": {...},
  "components": [
    {"type": "metric", "title": "...", "valueRef": "..."},
    {"type": "bar", "title": "...", "dataRef": "...", "x": "...", "y": "..."}
  ]
}

Validate this specification before rendering.

RENDERER
Use a controlled component renderer. Supported concepts include metric, bar, line, area, scatter, table, map, text, formula, filter and section/container. Only supported types may render.

SEPARATION
Analytical result and presentation specification are different objects. Changing color, chart type, size or layout must not silently change the analytical result.

DESIGN
The product should feel like a professional analytical dashboard/research workspace, not a chatbot or static statistics page.
Use coherent typography, spacing, colors, contrast, hierarchy, responsive grids and restrained decoration.
Do not make every generated view visually random.

GENERATED DASHBOARD RULES
Prefer:
- line charts for time trends;
- bars for comparisons/rankings;
- maps for meaningful geography;
- tables for exact values;
- KPI cards for a small number of headline metrics.

Avoid unnecessary visualizations, excessive colors, tiny text and decorative charts.
Prefer roughly 3-6 meaningful major components for an ordinary analytical question unless the data requires otherwise.

INTERACTION
Support, where valid:
- resize;
- reorder;
- expand/focus;
- collapse;
- filters;
- sorting;
- table search;
- valid visualization switching;
- supported color/theme customization;
- reset;
- undo/revert.

Do not regenerate the whole workspace for a local interaction.

RESPONSIVE
Support desktop, tablet and mobile.
Use sensible component minimum/maximum sizes.
On small screens, collapse columns, allow focused charts, and provide usable table overflow or focused views.

PLAYGROUND
Provide an advanced playground with:
- presentation specification editor;
- live preview;
- validation errors;
- component inspector;
- undo/revert;
- save-as-new-version.

The playground is a controlled authoring environment, NOT arbitrary code execution.

HISTORY
Each completed analysis is an analytical artifact containing:
- user question;
- analytical result;
- sources;
- presentation specification;
- user customizations;
- model/analysis version metadata;
- timestamps;
- artifact version.

History should feel like saved analytical work, not chat messages.
A history item should have a meaningful title, preview where practical, date/context and open/continue action.

REPRODUCIBILITY
Reopening restores layout, component configuration, filters, customization, specification and source references.
If source/model versions have changed, make that visible rather than silently rewriting old results.

ACCESSIBILITY
Implement:
- keyboard navigation;
- semantic structure;
- screen-reader labels;
- visible focus;
- high contrast;
- text scaling;
- reduced motion;
- no color-only semantics;
- chart text summaries;
- accessible data tables;
- clear error messages.

VOICE
Voice is optional and must use the normal analytical pipeline:
audio -> speech recognition -> visible transcript -> normal request -> dashboard.
Typed input always remains available.
Text-to-speech reads dashboard insights while the same content remains visible.

DEAF ACCESSIBILITY
Never require hearing. Audio must have text alternatives. Voice transcripts must be visible. Notifications need visual alternatives.

DATA TRUST
Never fabricate frontend values.
Never hardcode fake statistics in production flows.
Never make the UI infer values that should come from analytical results.
Displayed values must be traceable to returned analytical data.

ERROR STATES
Design proper states for loading, no data, ambiguous question, unsupported analysis, invalid presentation specification, model failure, data-source failure, partial result and access limitation.
Do not show fake content while waiting.

SECURITY
Never execute arbitrary model-generated HTML/JavaScript.
Never use eval-like execution.
Validate presentation specifications strictly.
Sanitize user content.
Protect secrets.

CODE QUALITY
Build reusable components.
Separate UI from business logic.
Centralize presentation schema/types.
Validate system boundaries.
Avoid duplicate chart/table logic.

DEVELOPMENT ORDER
1. Presentation schema.
2. Renderer.
3. Core visualization components.
4. Workspace layout/resizing.
5. Analytical-result integration.
6. History/artifacts.
7. Playground.
8. AI generation integration.
9. Voice/accessibility enhancements.
10. Responsive polish and testing with real analytical outputs.

FINAL PRODUCT RULE
The AI-generated result is NOT the interface itself.
It is a structured description of an analytical interface.
The product owns rendering, design, security, accessibility and interaction behavior.
